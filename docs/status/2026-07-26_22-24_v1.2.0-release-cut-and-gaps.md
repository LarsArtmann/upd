### The annotated-tag SHA false alarm (worth remembering)

When publishing, a pre-flight check compared local vs remote tag SHAs and looked divergent:

- `git ls-remote --tags origin v1.2.0` → `d01d3c3…`
- my local tag had been created on commit `da289c9`

This looked like the tag had been moved/clobbered by the daemon. **It had not.** The explanation is mundane but easy to misread:

- `v1.2.0` is an **annotated tag**, which is a _separate git object_ (type `tag`), not the commit itself.
- `git rev-parse v1.2.0` / `git ls-remote` returns the **tag object's own SHA** (`d01d3c3`).
- That tag object **points to** commit `da289c9` — confirmed via `git cat-file -p v1.2.0` (`object da289c9…` / `type commit`) and `git rev-parse v1.2.0^{commit}` → `da289c9`.

So nothing was damaged or moved. `git log --decorate` correctly shows `da289c9 (tag: v1.2.0)` because it dereferences the tag object. **Lesson:** when comparing annotated tags across local/remote, always deref with `^{commit}` (or compare `refs/tags/<name>^{}` from `ls-remote`) — never compare the raw tag-object SHA to a commit SHA.
